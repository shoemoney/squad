### Structural consequences of D35 to D38

- Milestone M4 is renamed **Desktop UI (Vue renderer)**. All "web", "browser", "responsive/mobile layout" requirements are rewritten for a resizable desktop window (minimum window size instead of mobile breakpoints).
- A new milestone **M4b Electron shell and packaging** is added after M4: main process, preload with a minimal typed IPC bridge (contextIsolation on, nodeIntegration off, sandboxed renderer), server lifecycle (D36), Redis setup screen (D37), native menus and shortcuts, window state persistence, markdown export via native save dialog, electron-builder config and CI build matrix for macOS arm64 and Linux x64 (D38).
- The OpenRouter key never reaches the renderer. It lives in the main/server process only.
- Electron security baseline: no remote content loaded, strict Content-Security-Policy, external links open in the system browser, navigation and new-window creation blocked.

### Pivot (owner, 2026-11-24, after round 4)

| ID | Decision |
|---|---|
| D49 | Squad is a TUI only. There is no Electron app, no Vue app and no browser client. D35, D36, D37, D38 and D47 are VOID. The web-only compare view in D13 is void (single timeline only). D24 becomes: several TUI instances may attach to the same room and stay in sync. Milestone M4 (desktop/web UI) and M9 (Electron) are removed. |
| D50 | The TUI framework is chosen from current research into the most performant options, not assumed to be Ink. |
| D51 | (Partly VOID by D54: there is no separate server, so `squad serve`, `squad tui`, attaching and the gateway are gone, and `squad debug bus` became `squad --bus-log` and the F12 debug pane.) The whole product is Rust. One `squad` binary contains the server (router, agents, orchestrator, gateway) and the TUI. The TUI is built on Ratatui + crossterm + tokio. `squad` starts the room and opens the TUI (attaching to a running server if one is listening); `squad serve` runs headless; `squad tui` attaches only; `squad send`, `squad export`, `squad debug bus` are one-shot. D9 (TypeScript stack) is VOID. Shared protocol lives in a Rust crate (serde), not zod. |
| D52 | Redis stays as the backbone: pub/sub for live traffic, Streams for durable history, exactly as designed. |
| D53 | The repo ships a `./setup.sh` that installs every dependency on macOS and Linux, so a fresh machine goes from clone to a running `squad` with one script. |
| D54 | NO Redis. Squad is one self-contained binary and one process: in-process channels for live traffic and a local SQLite file for durable history. Each model still has its own private mailbox and private history. The bus sits behind a trait so a networked backend can be added after v1. v1 is one front end per room (no second TUI attaching). D24, D33 and D52 are VOID; D53's setup script installs no Redis. |
| D55 | `ROUNDS` defaults to 10 (min 1, max 20). Supersedes the default of 3 and max of 10 in D15. |
| D56 | All configuration is one `.env` file: the OpenRouter key, the rounds, and the model slugs, shipped as `.env.example` pre-populated with the six default members. There is no `squad.toml`. The roster is whatever `SQUAD_MODEL_<NICK>` lines exist. Supersedes the config-file wording in D32, D41, D42 and D46 (those settings become optional env vars). |
| D57 | The judge scores every debate round. After each round's two turns are committed, the judge (the same case context for the whole debate, still with no room memory) scores both debaters 1 to 10 for that round with a one-line reason each. The user sees a live running scorecard. Debaters do NOT see round scores until the final verdict. The next round starts without waiting for the round score. The final verdict remains the judge's overall decision; if its winner differs from the round-tally leader it must say why. |
| D58 | Between rounds the TUI shows an ASCII-art banner (FIGlet style, like `echo ROUND 1 \| toilet`): `ROUND n`, `FINAL ROUND`, `VERDICT`. Rendered in-process from a font embedded in the binary, never by shelling out. Falls back to a one-line divider when the terminal is too narrow. Included in markdown export as a code block. |
| D59 | The TUI goes heavy on visual effects and flair: animated banners, reveals, gradients, a verdict sequence, per-model colour identity. Effects must never cost smoothness or readability, must degrade on limited terminals, and can be turned down or off (`SQUAD_FX`). |
| D60 | Squad is released under the Apache License 2.0 (supersedes MIT in D34). The repo ships `LICENSE` and `NOTICE`; every crate sets `license = "Apache-2.0"`; embedded fonts and other vendored assets must be Apache-2.0 compatible and are credited in `NOTICE`. Publishing remains an explicit owner decision. |
| D61 | Squad is built in public from day one. The repo is `github.com/shoemoney/squad`, public, created 2026-11-24. Supersedes the "private until launch" part of D34 and the private-repo part of D48. |
| D62 | The owner's local `.env` takes its OpenRouter key from his own key vault. This is local setup only; the repo and `setup.sh` know nothing about any vault. |
| D63 | Build approach: most coding units go to the GPT Sol 6.1 worker on its fast tier, dispatched asynchronously with the widest fan-out each milestone allows (one git worktree per worker, merged by the orchestrator); overflow goes to the other coding workers; one review pass per milestone. Refines D48. |
| D64 | A daily spend bar is always visible (`$spent ▰▰▱▱ $max`). The max is `SQUAD_DAILY_MAX_USD` in `.env` (default 20). Spend is the real cost OpenRouter reports per call. At the max Squad stops sending new requests until the next local day or until the max is raised. This replaces the separate room budget in D22 (the debate confirmation threshold stays). |
| D65 | `$tournament`: every named entrant (or `@all`) answers; the judge ranks all answers with scores and critiques; the lowest-ranked is eliminated; survivors are told their own result and present again; repeat until one champion remains. Entrants see only their own results. Judging is blind (anonymised, shuffled labels), so Fable stays the judge even when it competes. One elimination per round. Minimum three entrants. |
| D66 | `$grill`: the user picks one model's plan (`@leader $grill`); every other model grills the leader one at a time on a shared floor that all grill participants can see; the leader answers and updates the plan after each griller; at the end of each round the leader rebuilds the full plan; repeat for `GRILL_ROUNDS` (default 2, `SQUAD_GRILL_ROUNDS` in `.env`). Up to 3 questions per turn; grillers may pass; if all pass the grill ends early. Output is the final plan plus a question-and-answer appendix. No judge. |
| D67 | Debate, tournament and grill share one contest engine; one contest runs at a time per room. Build order: debate, then tournament, then grill. |
| D68 | Modes can start from the question: `@all $debate <question>` → everyone answers → banner `CHOOSE YOUR DEBATE BROS` → the user picks two by typing `@a @b` → the debate runs. Same for `$grill` with `CHOOSE WHO GETS GRILLED` and one pick. The direct forms (`@a @b $debate`, `@leader $grill`) remain as shortcuts. The room stays usable while a pick is pending; Esc cancels and the answers remain ordinary replies. |
| D69 | `$survey` and `$probe` are v1 modes. `$survey` maps where the room agrees claim by claim; `$probe` turns a mystery into a decision tree of checks. Both were proposed by the room's own models in a blind test run. |
| D70 | `$census` (Fable's design: lens-assigned blind gap hunt, merged ledger, everyone rates each gap, and a capture-recapture estimate of gaps still unfound) and `$crosscheck` (OpenAI's design: a coverage grid built blind to the plan, checked cell by cell including every cross-lens pair) are v1 modes. Squad's stated purpose is to produce the ultimate plan, one where everything has been thought of. |
| D71 | All seven modes are scripts over one engine's shared moves. Build order: debate, grill, census, crosscheck, tournament, survey, probe. Supersedes the order in D67. |
| D72 | Census estimate range (owner decision 2026-11-25): the Chao (1987) log-normal interval around the Chao1 unseen estimate `U`. With `f1`, `f2`, `S_obs` = confirmed gaps found (confirmed ledger gaps plus rating additions): variance is `f2·[½(f1/f2)² + (f1/f2)³ + ¼(f1/f2)⁴]` when `f2 > 0`, else `f1(f1−1)/2 + f1(2f1−1)²/4 − f1⁴/(4·Ŝ)` with `Ŝ = S_obs + U`, clamped at 0. If `U > 0`: `K = exp(1.96·√ln(1 + var/U²))`, `lo = U/K`, `hi = U·K`. If `U = 0`: `lo = hi = 0`. If `S_obs = 0`: no range, the report says `Nothing found yet.`. Shown to one decimal, stored unrounded in `estimateLow`/`estimateHigh`. Called a plausible range, never a confidence interval; the shared-blind-spots caveat stays. Quiet (`Census is quiet. Good place to stop.`) requires `hi < 2`, no new confirmed gap this pass, no missing participants and no unresolved rating evidence. |

### Tune and bass_ackwards (owner, 2026-11-26)

The owner approved two more modes: `$tune`, his first pick from the second brainstorm round, and `$bass_ackwards_prd`, his own design in its upgraded form. [Tune and bass_ackwards](12-tune-and-bass-ackwards.md) is the binding specification; these rows record the choices made in it.

| ID | Decision |
|---|---|
| D88 | Two modes are added, names final: `$tune` (Rust `Tune`, module `tune`, migration 0019) and `$bass_ackwards_prd` (Rust `BassAckwardsPrd`, module `bass_ackwards_prd`, migration 0020, explicit serde renames as for `blow_it_up`). Both are scripts over the shared engine and follow D74: one registry scaffold, then the two modes in parallel in their own files behind `ENABLED` switches, then one integration pass (milestone M9). Artifacts travel in `contest.artifact`. |
| D89 | Two room variables: `TUNE_GENERATIONS` (default 3, 1 to 6) and `PRD_HUMAN_REVIEW` (default 0, 0 or 1), with optional `SQUAD_<NAME>` seeds that are not in `.env.example`. An admitted contest keeps its frozen value. |
| D90 | The engine gains an executor call, a third work class beside member and judge calls, used by `tune.execute`. The request is bare: the candidate prompt as the system message and the case input as the user message, or one user message when the prompt carries `{{input}}`, sent byte for byte with no Squad prompt, persona, history or redaction. 180 s, 2 plain attempts, no repair, 1,024 visible tokens. Reserved attempts become `2 × member + 2 × executor + 3 × judge` calls. This extends D75. |
| D91 | `$tune`: members build the test set blind (up to three cases and three criteria each). The judge selects four to six cases and two to four criteria and writes none; a frozen case is byte-identical to its proposal and at most two come from one member. The app, not the judge, splits train and held-out by a persisted seed. No prompt author ever receives a case, an expectation, a rubric description, an output or anything about the held-out set; the only feedback is a digest of the champion's train scores and short notes, and a note that copies six consecutive words of its case is rejected. Outputs are scored 0 to 4 per criterion by a blind judge that never sees a prompt; the original's and the champion's stored outputs are scored again in every sheet so no comparison crosses judge calls. A generation's best replaces the champion only with a gain of at least 0.05. The final pick is made on held-out scores alone, among the original, the final champion and the champion before it, and a variant wins only by beating the original there by at least 0.05. Scores, promotion and the pick are application code. |
| D92 | The `$tune` executor is the judge's model by default, called bare. Chosen over a member because one fixed model then produces every output, the scorer is blind to which candidate produced which output, so a preference for the executor's own style is constant across candidates, and no author executes its own prompt. `-- @nick` names a roster member as executor to tune for the model that will run the prompt; that member leaves the participants and writes nothing. |
| D93 | `$tune` cost caps are constants: at most six frozen cases (three train, three held-out), three mutators per generation dealt by a seeded rotation, at most three finalists, one executor call per candidate and case and never a repeat, one scoring call per pass covering all its cases, prompts capped at 1,200 words and variants at `min(1,800, max(⌈1.5 × W0⌉, W0 + 150))`. Calls are at most `m + T + 3H + 3 + G(3T + 4)`, reserved at the caps as `m + 13G + 15` normal calls and `2m + 27G + 33` attempts; six members at G of 3 cost at most 60, of which 39 are executor calls. The brainstorm's every-member-mutates and score-per-output designs were rejected because executions grow as cases × candidates × generations. |
| D94 | `$bass_ackwards_prd` (owner's upgraded flow): done first, then backward. Members write acceptance tests blind; the judge only groups equivalent items and the app freezes those named by at least two members, at most twelve by support, never reworded or added to. Each member then builds a blind precondition tree back from the end result (at most 20 nodes, depth 4, every node serving a DoD item). A blind judge merges the trees into one dependency graph and writes the PRD in house style, with every line item citing a source node and at least one DoD item and no item depending on a later milestone. Review, revision, a capped must-have round and a final assembly follow, then app checks and an automatic save. `4m + 4` calls, `8m + 12` reserved attempts; six members cost 28. The critical path and parallel levels are computed by the app from the graph and no durations are estimated. |
| D95 | PRD review is targeted, not open. Each member gets one lens dealt round-robin from a seeded shuffle: `GAPS`, `ATTACK` or `READBACK` (state what you would build from one assigned milestone). Every comment must quote the PRD passage it targets; the shared `verbatim` matcher decides, and a comment whose quote fails is dropped without repair. The last round allows up to three must-have additions per member and its schema cannot express a change or removal. |
| D96 | PRD revision integrity. The app mints permanent keys for every milestone, phase and line item; display numbers are positional. The judge records accept or reject with a one-line reason for every comment and addition. After a revision, anything no accepted decision names must be byte-identical; after the final assembly, every existing item is byte-identical and in place and only additions are new. The judge adds no line item without a member or human source and cannot edit the frozen definition of done. |
| D97 | Four app checks run before the save: every line item maps to a DoD item, every DoD item is served, no dangling dependency, no cycle. There is no extra judge repair call. The three structural checks are also validation rules on every judge output, so they are repaired inside that call's own three attempts. Coverage is not forced on the judge, because covering a DoD item no member addressed would make the judge the author of unreviewed work; the uncovered list is instead handed to the `GAPS` reviewers and the must-have round. What still fails is written into the PRD's appendix and the report's first line, with terminal reason `saved_with_findings`. |
| D98 | The PRD is saved automatically to `<data_dir>/exports/prd-<slug>-<contestId>.md`, the first file the core writes on its own. The data directory was chosen over the working directory because it is always present, writable and the same after a restart or from `squad send`. The path is a pure function of committed records, the report is committed before the write, and the write is a temporary file renamed into place, so recovery rewrites the same bytes. A failed write completes with `save_failed`; `/export bass_ackwards_prd [id]` always works. A revision or final-assembly judge failure still saves the last good version; a merge failure saves nothing. |
| D99 | `$bass_ackwards_prd` has an optional human step before the save, off by default (`PRD_HUMAN_REVIEW=1` turns it on). Off because the flow is one command in and one file out, and a human step waits without expiry, holds the room's claim and stops a one-shot `squad send` before the file exists. Offered because only the human knows whether the end result was understood. Human notes are instructions: the judge applies them in one extra call and cannot reject one. At most `4m + 5` calls and `8m + 15` reserved attempts. `$tune` has no human step. |
| D100 | M9 adds no MCP tool, as D87 did for M8. `tune` and `bass_ackwards_prd` (with human review off) are candidates for a later milestone. |
